## 2. Особливості реалізації варіанта №3

### 2.1. Основне технічне обмеження

У проєкті використовується MongoDB, але організація даних повинна відповідати принципам нормалізації реляційних баз даних.

Це означає, що MongoDB використовується не за типовим підходом із великими вкладеними документами, а як набір окремих логічно пов'язаних колекцій.

### 2.2. Правила організації даних

| № | Правило |
|---|---|
| DB-01 | Кожна самостійна сутність зберігається в окремій колекції |
| DB-02 | Кожен документ має унікальний ідентифікатор `_id` |
| DB-03 | Зв'язки між документами реалізуються через ObjectId |
| DB-04 | Зв'язки багато-до-багатьох реалізуються через проміжні колекції |
| DB-05 | Повторне зберігання довідкових даних в інших сутностях не допускається |
| DB-06 | Перевірка існування пов'язаних документів виконується сервером |
| DB-07 | Унікальність критичних даних забезпечується індексами |
| DB-08 | Видалення записів не повинно порушувати цілісність пов'язаних даних |
| DB-09 | Для багатокрокових критичних операцій передбачаються транзакції |
| DB-10 | Історичні фінансові значення зберігаються незалежно від поточних тарифів |

### 2.3. Приклад нормалізації

Замість зберігання батьків безпосередньо всередині документа дитини використовуються окремі колекції.

Колекція `children`:

```json
{
  "_id": "ObjectId",
  "firstName": "Андрій",
  "lastName": "Петренко",
  "birthDate": "2022-05-10",
  "status": "ACTIVE"
}
```

Колекція `parents`:

```json
{
  "_id": "ObjectId",
  "firstName": "Олена",
  "lastName": "Петренко",
  "phone": "+380991234567"
}
```

Колекція `child_parents`:

```json
{
  "_id": "ObjectId",
  "childId": "ObjectId",
  "parentId": "ObjectId",
  "relationship": "MOTHER"
}
```

Наведені значення ObjectId є умовними позначеннями типів. У MongoDB ці поля зберігаються як справжні ObjectId.

Така структура дозволяє пов'язувати одну дитину з кількома батьками, а одного з батьків — із кількома дітьми.

### 2.4. Забезпечення цілісності

На відміну від реляційних СУБД, MongoDB не забезпечує звичайні зовнішні ключі з автоматичним контролем посилальної цілісності.

Тому застосунок повинен самостійно:

- перевіряти існування пов'язаних документів;
- запобігати створенню некоректних зв'язків;
- перевіряти унікальність призначень;
- контролювати видалення пов'язаних записів;
- використовувати транзакції для операцій, що змінюють кілька колекцій.

Для роботи транзакцій MongoDB повинна підтримувати replica set.

У цьому проєкті використовується MongoDB Atlas, який забезпечує необхідну конфігурацію replica set без ручного налаштування Docker.

- Користувачі без необхідних прав отримують HTTP 403.
- Обліковий запис користувача та інформація про працівника або батька є різними сутностями.

## 5. Управління дітьми та сім'ями

### 5.1. Реєстрація дітей

Для кожної дитини зберігається:

- дата народження;
- дата зарахування;
- поточний статус;
- інформація про харчові обмеження;
- додаткові відомості;
- зв'язки із законними представниками.

Вік розраховується за датою народження, а не зберігається як постійне числове поле.

### 5.2. Бізнес-обмеження

- Приймаються діти віком 2–5 років.
- Дитина може мати кількох законних представників.
- Один із батьків може бути пов'язаний із кількома дітьми.
- Дитина може перебувати лише в одній активній групі одночасно.
- Інформація про попередні групи не повинна втрачатися.

### 5.3. Переведення між групами

Переведення дитини виконується як окрема операція.

Система повинна:

1. Перевірити існування дитини.
2. Перевірити цільову групу.
3. Переконатися, що вік дитини відповідає групі.
4. Перевірити наявність вільного місця.
5. Завершити попереднє активне зарахування.
6. Створити новий запис зарахування.
7. Зберегти історію операції.

Операція повинна виконуватися атомарно, щоб дитина не опинилася одночасно у двох активних групах.

## 6. Групи та приміщення

### 6.1. Формування груп

Групи створюються відповідно до вікових категорій дітей.

|---|---|---|

| A5 | 5 років | 20 |

Це приклади назв. Система може підтримувати кілька груп одного віку.

### 6.2. Обмеження груп

- Усі діти однієї групи повинні належати до визначеної вікової категорії.
- Кількість активних дітей не перевищує 20.
- Кожна діюча група має одного вихователя та одного помічника.
- Кожна група використовує окрему основну кімнату.
- Одна кімната не може одночасно бути основною для двох діючих груп.
- Переповнення групи забороняється незалежно від ролі користувача.

### 6.3. Управління кімнатами

У системі передбачено 20 приміщень.

Для кожного приміщення зберігаються:

- номер або назва;
- призначення;
- статус доступності;
- максимальна місткість;
- активне закріплення за групою, якщо воно існує.

Приміщення можуть використовуватися як основні кімнати груп або як спеціалізовані кімнати для занять.

Система повинна перевіряти конфлікти використання приміщень.

### 6.4. Уточнення правил використання приміщень (відповідь викладача)

- Одна група може проводити заняття у спеціалізованій кімнаті, навіть якщо її основна кімната вільна.
- Одне приміщення одночасно може використовувати лише одна група, зокрема це стосується спортзалу.
- Різні групи можуть використовувати спеціалізовану кімнату в різний час.
- Під час складання розкладу сервер перевіряє перетини часових інтервалів для приміщень.

## 7. Персонал дитячого садка

### 7.1. Категорії працівників

Інформація про працівника зберігається окремо від його облікового запису.

### 7.2. Початкові ставки

| Посада | Правило нарахування |
|---|---|
| Менеджер | 80 000 грн/міс. |
| Викладач | 40 000 грн/міс. |

| Помічник | 20 000 грн/міс. |

Якщо у групі більше 12 дітей, застосовуються доплати.

| Посада | Доплата за кожну дитину понад 12 |
|---|---|
| Вихователь | 5 000 грн |
| Помічник | 3 000 грн |

### 7.3. Формули нарахування

Зарплата вихователя:

```text
EducatorSalary =
    2000 * ChildrenCount
    + 5000 * max(0, ChildrenCount - 12)
```

Зарплата помічника:

```text
AssistantSalary =
    20000
    + 3000 * max(0, ChildrenCount - 12)
```

Приклад для групи з 15 дітей:

| Працівник | Розрахунок | Зарплата |
|---|---|---|
| Вихователь | 15 × 2 000 + 3 × 5 000 | 45 000 грн |
| Помічник | 20 000 + 3 × 3 000 | 29 000 грн |
| Разом | | 74 000 грн |

Кількість дітей для розрахунку зарплати визначається за погодженим розрахунковим правилом.

У базі повинна зберігатися історія ставок, щоб зміна зарплати не змінювала попередні нарахування.

### 7.4. Призначення вихователів (відповідь викладача)

- Один вихователь закріплюється за однією групою; одночасне призначення до двох груп заборонене.
- У межах умов проєкту вихователі не хворіють, тому механізм лікарняних і замін через хворобу не розробляється.
- Історія призначень зберігається, а поточні призначення перевіряються на конфлікти.

### 7.5. Історія нарахувань

- `SalaryCalculation` зберігає `employeeId`, `periodYear`, `periodMonth`, `baseAmount`, `finalAmount`.
- Для одного працівника за один розрахунковий місяць і рік не створюється два звичайні нарахування.
- Попередні нарахування не змінюються після оновлення ставок і не видаляються фізично.

## 8. Освітній процес і розклад

### 8.1. Навчальні дисципліни

Початковий перелік:

| Дисципліна | Призначення |
|---|---|
| Музика | Музичний розвиток |
| Англійська мова | Основи іноземної мови |
| Фізкультура | Фізичний розвиток |
| Вільна боротьба | Спортивна підготовка |
| Шахи | Розвиток логічного мислення |

Адміністратор може додавати нові дисципліни та призначати викладачів.

### 8.2. Організація дня

Робочий день триває 8 годин, тобто 480 хвилин.

Обов'язкові блоки:

| Активність | Тривалість |
|---|---|
| Денний сон | 60 хв |
| Сніданок | 30 хв |
| Обід | 30 хв |
| Полуденок | 30 хв |
| Заняття | За налаштуваннями |
| Вільний час | Решта доступного часу |

Після врахування сну та харчування залишається 330 хвилин на заняття, перерви й вільний час.

### 8.3. Перевірка розкладу

Система не допускає:

- одночасного проведення двох занять одним викладачем;
- використання однієї кімнати двома групами в один час;
- накладання занять однієї групи;
- занять під час сну або харчування;
- виходу занять за межі робочого дня;
- нерівномірного обов'язкового навчального навантаження між групами одного віку.

Розклад має два стани:

- DRAFT — створюється або редагується;
- PUBLISHED — перевірений і доступний для перегляду.

Автоматичне формування розкладу реалізується на наступному етапі після створення базових операцій із заняттями.

## 9. Оплата навчання та харчування

### 9.1. Навчання

Базова місячна вартість навчання:

15 000 грн за одну дитину.

Адміністратор може змінювати тариф, але нова ціна не повинна змінювати вже сформовані рахунки.

### 9.2. Харчування

| Вік дитини | Вартість за день |
|---|---|
| 2 роки | 300 грн |
| 3 роки | 400 грн |
| 4 роки | 500 грн |
| 5 років | 600 грн |

Формула:

```text
DailyMealPrice = 300 + (Age - 2) * 100

MealTotal = DailyMealPrice * MealDays
```

Кількість оплачуваних днів задається для конкретного розрахункового періоду.

### 9.3. Пільги

Передбачені три рівні пільг:

- 10%;
- 20%;
- 30%.

Пільги застосовуються лише до навчання.

```text
TuitionAfterDiscount =
    BaseTuition * (1 - DiscountRate)
```

Приклад:

```text
15000 * (1 - 0.20) = 12000 грн
```

### 9.4. Місячний платіж

```text
MonthlyAmount =
    TuitionAfterDiscount + MealTotal
```

Для дитини 3 років із пільгою 20% та 20 оплачуваними днями:

| Складова | Сума |
|---|---|
| Навчання | 15 000 грн |
| Пільга 20% | −3 000 грн |
| Харчування | 8 000 грн |
| До оплати | 20 000 грн |

### 9.5. Річна оплата

Передбачена можливість оплати за 12 місяців наперед.

Додаткова знижка — 12% на навчання.

Знижки застосовуються послідовно:

```text
AnnualTuition =
    BaseTuition
    * (1 - DiscountRate)
    * 12
    * 0.88
```

Харчування оплачується окремо.

Спеціальна знижка за наявність кількох дітей в одній сім'ї не передбачена.

---

### 9.6. Уточнення вікового тарифу (відповідь викладача)

- День народження посеред місяця не спричиняє автоматичного переходу на інший тариф харчування.
- Дитина продовжує відвідувати ту саму вікову групу; тариф харчування визначається за її чинною групою.
- Пільга 10/20/30% і річна знижка 12% застосовуються послідовно, шляхом множення коефіцієнтів, а не додавання відсотків.

### 9.7. Версіонування тарифів

- Кожна зміна тарифу створює нову версію з `validFrom`; попередні версії не перезаписуються.
- Рядок рахунка `InvoiceLine` зберігає `tariffSnapshot` — застосовану ціну та версію тарифу на дату формування.
- Зміна поточного тарифу не перераховує вже сформовані рахунки.

## 10. Рахунки та платежі

Для коректного фінансового обліку система розділяє нарахування й фактичні платежі.

### 10.1. Рахунок (Invoice)

Рахунок містить:

- дитину;
- платника;
- розрахунковий період;
- тариф навчання;
- застосовані знижки;
- вартість харчування;
- підсумкову суму;
- дату створення;
- статус оплати.

Суми у сформованому рахунку фіксуються і не перераховуються автоматично після зміни тарифів.

### 10.2. Платіж (Payment)

Платіж містить:

- суму;
- дату;
- платника;
- спосіб оплати;
- унікальний ідентифікатор операції;
- зв'язок із відповідним рахунком або рахунками.

### 10.3. Основні правила

- Створення рахунка не означає отримання коштів.
- Один рахунок може бути оплачений кількома платежами.
- Один платіж може бути розподілений між кількома рахунками.
- Повторний запит з однаковим ідентифікатором операції не створює дубліката платежу.
- Система повинна визначати залишок заборгованості.
- Фінансові записи не видаляються звичайними CRUD-операціями.
- Для розподілу платежів використовується окрема проміжна колекція `payment_allocations`.

---

### 10.4. Деталізація та захист фінансових записів

- `InvoiceLine` зберігає складові рахунка, суму та знімок застосованого тарифу.
- `PaymentAllocation` пов'язує платежі з рахунками й дозволяє одному платежу покривати кілька рахунків, а одному рахунку — отримувати кілька платежів.
- `Invoice`, `Payment` і `SalaryCalculation` не видаляються фізично; скасування й коригування оформлюються контрольованими операціями.
- Для рахунків пропонується унікальність `(childId, periodYear, periodMonth, type)`. Річні та місячні нарахування потрібно перевіряти також на змістове дублювання періодів.
- Для кожного платежу потрібен унікальний ключ ідемпотентності, включно з ручними платежами. Перевірка лише за сумою й часом не є достатньою.

## 11. Фінансовий облік

### 11.1. Джерела доходу

Основні джерела:

- оплата навчання;
- оплата харчування.

Для звітів потрібно розрізняти нараховані суми та фактично отримані платежі.

### 11.2. Витрати

До витрат належать:

- заробітна плата менеджера;
- заробітна плата вихователів;
- заробітна плата помічників;
- заробітна плата викладачів;
- фактична закупівля харчування;
- інші операційні витрати.

Вартість харчування для батьків і фактична собівартість харчування обліковуються окремо.

### 11.3. Використання приміщень

Приміщення належать власнику садочка.

Для економічного моделювання використовується нормативна вартість:

50 000 грн на місяць за кімнату.

Це не фактична орендна плата, а умовний показник для оцінки економічної ефективності.

### 11.4. Розрахунок прибутку

Операційний прибуток:

```text
OperatingProfit =
    TotalRevenue - ActualExpenses
```

Модельний прибуток:

```text
ModelProfit =
    OperatingProfit
    - 50000 * UsedRooms
```

Обидва показники повинні відображатися окремо.

Річні передоплати не можна повністю зараховувати до доходу одного місяця у звіті за методом нарахування.

## 12. Аналітика та прогнозування

Аналітичний модуль призначений для оцінки економічної ефективності дитячого садка.

### 12.1. Основні звіти

Система повинна надавати:

- кількість дітей за віком;
- заповненість груп;
- кількість зайнятих кімнат;
- витрати на персонал;
- нараховані платежі;
- фактично отримані кошти;
- заборгованість;
- прибуток окремих груп;
- загальний прибуток садочка.

### 12.2. Моделювання кількості дітей

Адміністратор може передати сценарій, наприклад:

```json
{
  "children": [
    {
      "age": 5,
      "count": 150
    }
  ],
  "includeRoomCost": true
}
```

Система повинна визначити:

1. Необхідну кількість груп.
2. Можливий розподіл дітей.
3. Кількість потрібних кімнат.
4. Кількість вихователів і помічників.
5. Витрати на персонал.
6. Очікувані доходи.
7. Очікувані витрати.
8. Прогнозований прибуток.

Для 150 дітей мінімальна кількість груп за місткістю становить:

```text
ceil(150 / 20) = 8 груп
```

Це лише перевірка місткості, а не гарантія найприбутковішого розподілу.

Оптимізація повинна враховувати доплати працівникам, доступні кімнати та інші витрати.

Повний алгоритм пошуку найвигіднішої конфігурації реалізується на наступному етапі.

| Колекція | Призначення |
|---|---|
| users | Облікові записи |
| parents | Законні представники |
| children | Дані дітей |
| child_parents | Зв'язки дітей і батьків |
| groups | Групи |
| group_enrollments | Зарахування та історія переведень |
| rooms | Приміщення |
| employees | Працівники |
| staff_assignments | Призначення працівників |
| subjects | Дисципліни |
| teacher_subjects | Зв'язки викладачів із дисциплінами |
| schedules | Версії розкладів |
| schedule_items | Окремі заняття |
| tuition_rates | Тарифи навчання |
| meal_rates | Тарифи харчування |
| discounts | Типи пільг |
| child_discounts | Призначені пільги |

| salary_rates | Історія ставок |
| expenses | Витрати |

Це попередня модель, яка уточнюватиметься під час створення `schema.prisma`.

### Основні зв'язки

| Зв'язок | Тип |
|---|---|
| Child — Parent | M:N |
| Child — Group | M:N через історію зарахувань |
| Group — Room | N:1 з обмеженням активних призначень |
| Group — Employee | Через StaffAssignment |
| Teacher — Subject | M:N |
| Schedule — ScheduleItem | 1:N |
| Child — Invoice | 1:N |
| Invoice — Payment | M:N через PaymentAllocation |

Для активних призначень необхідно передбачити перевірки, які не дозволять створювати конфліктні записи.

---

### 13.1. Уточнення моделі колекцій MongoDB (версія 2)

Модель залишається нормалізованою: сутності зберігаються окремо, зв'язки оформлюються через `ObjectId`, а зв'язки M:N — через явні проміжні колекції.

| Сутність / колекція | Основні поля або призначення | Обмеження |
|---|---|---|
| `Child` | `firstName`, `lastName`, `birthDate`, `status`, `childCode` | Унікальний `childCode` |
| `Parent` | `firstName`, `lastName`, `phone`, `email` | Унікальний `email`, якщо заданий |
| `ChildParent` | `childId`, `parentId`, `relation` | Унікальна пара `(childId, parentId)` |
| `Group` | `name`, `ageFromMonths`, `ageToMonths`, `capacity` | Унікальна назва |
| `GroupEnrollment` | `childId`, `groupId`, `startDate`, `endDate` | Не більше одного активного зарахування |
| `Employee` | `firstName`, `lastName`, `role`, `employeeCode` | Унікальний `employeeCode` |
| `Room` | `name`, `capacity`, `status` | Унікальна назва |
| `Activity` / `Subject` | Довідник занять або дисциплін | Узгодити остаточну назву моделі |
| `Schedule` / `ScheduleItem` | Версії розкладів та окремі заняття | Контроль часових конфліктів |
| `Tariff` | `type`, `amount`, `validFrom` | Версійність тарифів; унікальність має враховувати вікову категорію |
| `Invoice` | `childId`, `periodYear`, `periodMonth`, `type`, `amountDue`, `status` | Контроль дублікатів |
| `InvoiceLine` | `invoiceId`, `description`, `amount`, `tariffSnapshot` | Історична ціна |
| `Payment` | `amount`, `paidAt`, `method`, `externalPaymentId` або внутрішній ключ | Ідемпотентність |
| `PaymentAllocation` | `paymentId`, `invoiceId`, `amount` | M:N між платежами та рахунками |
| `SalaryCalculation` | `employeeId`, `periodYear`, `periodMonth`, `baseAmount`, `finalAmount` | Історія нарахувань |
| `AuditLog` | Хто, коли, що і як змінив | Журнал важливих операцій |

Назви Prisma-моделей та фактичних MongoDB-колекцій можуть відрізнятися через `@@map`; остаточну схему узгоджують розробники.

### 13.2. Архівування та історія

- Для дітей, батьків, груп, працівників і приміщень використовується `soft delete` (`status`, `isActive`, за потреби `archivedAt`).
- Фінансові документи та історичні тарифи фізично не видаляються.
- Історія зарахувань, призначень і нарахувань повинна залишатися доступною після архівування пов'язаних довідникових записів.

### 13.3. Аудит — пропозиція команди

Викладач залишив вибір операцій аудиту на розсуд розробників. Пропонується фіксувати зміни тарифів і ставок зарплат, призначення пільг, переведення дітей, зміни призначень персоналу, зміни ролей, створення/скасування/коригування рахунків і платежів. Запис аудиту містить ідентифікатор користувача, час, сутність, тип операції та змінені значення без розголошення секретів.

### 13.4. Транзакції — пропозиція команди

Транзакції застосовуються для атомарного переведення дитини між групами, створення рахунка з рядками, реєстрації платежу з розподілом за рахунками та узгодженого фінансового коригування. Критичні пов'язані зміни або виконуються всі, або не виконується жодна.

Наведені endpoint-и є планом реалізації, а не переліком уже готових маршрутів.

### Формат успішної відповіді

```json
{
```

```json

  "error": {
```

## 18. Організація командної розробки

Усі учасники працюють з одним GitHub-репозиторієм.

### 18.1. Основні правила

- Гілка `main` містить перевірений код.
- Нові функції розробляються в окремих гілках.
- Прямі зміни в `main` не рекомендуються.
- Кожна завершена задача оформлюється через Pull Request.
- Перед злиттям код проходить перевірку.
- Конфігураційні секрети не додаються до репозиторію.
- Зміни структури бази даних узгоджуються з Team Lead.
- Кожен розробник відповідає за перевірку свого модуля.

### 18.2. Приклади назв гілок

```text
feature/auth
feature/children
feature/groups
feature/employees
feature/schedule
feature/billing
feature/analytics
fix/group-validation
docs/api
```

### 18.3. Клонування репозиторію

```bash
git clone https://github.com/juggermage/Node.js.git
cd Node.js
code .
```

### 18.4. Створення власної гілки

```bash
git switch main
git pull origin main
git switch -c feature/children
```

### 18.5. Збереження змін

```bash
git add .
git commit -m "feat: add children module"
git push -u origin feature/children
```

Після цього на GitHub створюється Pull Request до `main`.

### 18.6. Оновлення локального проєкту

```bash
git switch main
git pull origin main
```

Перед початком нової задачі розробник створює гілку від актуального `main`.

### 18.7. Правила Pull Request

Кожен PR повинен містити:

- короткий опис змін;
- посилання на відповідне завдання;
- перелік реалізованих функцій;
- інформацію про перевірку;
- за потреби — приклади HTTP-запитів.

Злиття виконується після перевірки відповідальним учасником або Team Lead.

### 18.8. Локальне налаштування середовища без Docker

Кожен розробник повинен мати:

- Node.js LTS;
- npm;
- Git;
- Visual Studio Code;
- доступ до MongoDB Atlas.

Docker Desktop не потрібен.

Після клонування репозиторію необхідно встановити залежності:

```bash
npm install
```

Команда встановлює бібліотеки, зазначені в `package.json`.

### 18.9. Підключення до MongoDB Atlas

Для зберігання даних використовується MongoDB Atlas.

Порядок налаштування:

1. Створити або отримати доступ до MongoDB Atlas.
2. Налаштувати базу даних для розробки.
3. Створити користувача бази з необхідними правами.
4. Дозволити підключення з потрібних IP-адрес.
5. Отримати рядок підключення MongoDB.
6. Зберегти рядок підключення у локальному файлі `.env`.

Для розробників рекомендується використовувати окремі бази або окремі середовища, щоб зміни одного учасника не пошкоджували дані інших.

Спільна тестова база може використовуватися для інтеграційного тестування після погодження правил роботи.

### 18.10. Змінні середовища

У репозиторії зберігається файл `.env.example` без справжніх паролів.

Приклад:

```env
PORT=3000
NODE_ENV=development

DATABASE_URL="mongodb+srv://USERNAME:PASSWORD@CLUSTER_HOST/kindergarten_dev?retryWrites=true&w=majority"

JWT_SECRET=replace_with_your_secret
```

Наведений рядок підключення є шаблоном.

Кожен розробник створює власний файл `.env`:

```powershell
Copy-Item .env.example .env
```

Після цього потрібно заповнити справжні значення.

Файл `.env` не додається до GitHub.

У `.gitignore` необхідно передбачити:

```gitignore
node_modules/
.env
.env.*
!.env.example
```

### 18.11. Налаштування Prisma

Після створення Prisma-схеми необхідно згенерувати Prisma Client:

```bash
npx prisma generate
```

Для синхронізації структури MongoDB зі схемою Prisma використовується:

```bash
npx prisma db push
```

Команда `prisma db push` застосовується лише після перевірки змін схеми та погодження з відповідальним розробником.

Для MongoDB не використовується звичайний процес Prisma Migrate, призначений для реляційних баз даних.

Конфігурація Prisma повинна відповідати версії Prisma, зафіксованій у проєкті.

### 18.12. Запуск сервера

Після встановлення залежностей і налаштування `.env` сервер запускається командою:

```bash
npm run dev
```

Команда працюватиме після додавання відповідного скрипту до `package.json`.

Приклад локальної адреси:

```text
http://localhost:3000
```

Початковий тестовий endpoint може мати вигляд:

```text
GET /api/v1/health
```

Очікувана відповідь:

```json
{
  "success": true,
  "message": "API is running"
}
```

Цей endpoint необхідно реалізувати під час початкового налаштування backend.

### 18.13. Робота з базою даних у команді

- Не змінювати спільну структуру Prisma без погодження.
- Не видаляти чужі тестові дані.
- Не використовувати реальні персональні дані дітей у тестовому середовищі.
- Не публікувати паролі MongoDB Atlas.
- Не додавати `.env` до комітів.
- Для інтеграційних тестів використовувати окрему тестову базу.
- Перед змінами структури колекцій перевіряти можливий вплив на інші модулі.

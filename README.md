# Система управління приватним дитячим садком

Варіант №3 — MongoDB, нормалізована як SQL

## 1. Мета проєкту

Серверна частина (backend) для обслуговування приватного дитячого садка: облік дітей і груп, розклад занять, розрахунок вартості для батьків та прибутку для власника.

Клієнтської частини немає. Це суто сервер із REST API.

## 2. Технічні обмеження

| № | Вимога |
|---|---|
| T1 | Дотримання принципів REST і робочий функціонал — головна вимога |
| T2 | База даних — MongoDB |
| T3 | MongoDB повинна бути нормалізована за принципами SQL |
| T4 | Дані зберігаються в окремих колекціях, подібно до таблиць реляційної бази даних |
| T5 | Зв'язки між колекціями реалізуються через ідентифікатори документів |
| T6 | Для зв'язків багато-до-багатьох використовуються проміжні колекції |
| T7 | Пов'язані дані не дублюються у вкладених документах |
| T8 | Для роботи з базою даних використовується Prisma ORM |
| T9 | Сервер реалізується на Node.js + Express |

## 3. Ролі користувачів

| Роль | Хто | Права |
|---|---|---|
| Admin | Власник (дід) | Бачить усе, зокрема прибуток. Змінює ціни, зарплати, вартість харчування, призначає пільги |
| Manager | Найманий менеджер (ЗП 80 000 грн) | Подібні можливості до Admin, але менший рівень доступу. Реєструє дітей |
| Parent | Батьки | Бачать тільки свою дитину: розклад її групи та вартість навчання. Можуть доповнювати дані про дитину. Чужих даних і знижок не бачать |
| Teacher | Викладач гуртка | Бачить власний розклад і може коригувати дозволені заняття |

## 4. Предметна область

### 4.1. Діти та батьки

- FR-01. У садок ходять діти віком 2–5 років.
- FR-02. Про кожну дитину зберігається інформація про батьків або опікунів.
- FR-03. Для дитини можна вказати родича-депутата або іншу важливу особу.
- FR-04. Додаткові дані про дитину (наприклад, «не любить гречку») вносять батьки.
- FR-05. Дитину реєструє Admin або Manager.
- FR-06. Одна сім'я може мати кілька дітей у садку.

### 4.2. Групи

- FR-07. У групі лише діти одного віку.
- FR-08. Максимум 20 дітей у групі. Жорстка межа.
- FR-09. У кожної групи є власне приміщення, вихователь і помічник.
- FR-10. Більше груп означає потребу в більшій кількості викладачів і приміщень.

### 4.3. Персонал

| Позиція | Зарплата, грн/міс |
|---|---|
| Викладач | 40 000 |
| Менеджер | 80 000 |
| Вихователь | Базова ставка + доплата |
| Помічник вихователя | Базова ставка + доплата |

- FR-11. Після 12-ї дитини в групі вихователь отримує +5 000 грн, а помічник +3 000 грн за кожну наступну дитину.
- FR-12. Admin може змінювати зарплати.
- FR-13. Приміщення коштує 50 000 грн/міс.

### 4.4. Гуртки та викладачі

- FR-14. Гуртки: музика, англійська, фізкультура, вільна боротьба, шахмати.
- FR-15. На кожен гурток потрібен викладач.
- FR-16. Кількість викладачів можна збільшувати у 2 або 3 рази, але лише за додатної окупності.

### 4.5. Розклад

- FR-17. Діти перебувають у садку 8 годин, з них 1 година сну.
- FR-18. Харчування: 3 прийоми по 30 хвилин, не підряд.
- FR-19. Дві групи не можуть бути на одному уроці одночасно.
- FR-20. Розклад рівномірний: кожна група має можливість відвідувати всі гуртки.
- FR-21. Система формує чернетку розкладу. Admin або викладачі можуть її коригувати.
- FR-22. Батьки бачать розклад групи своєї дитини. Викладач бачить власний розклад.

### 4.6. Вартість і оплата

- FR-23. Навчання коштує 15 000 грн/міс без харчування.
- FR-24. Пільги: три види зі знижкою 10%, 20%, 30%. Родичам Admin призначає максимальну, знайомим середню.
- FR-25. Харчування оплачується окремо, ціна залежить від віку: 300 грн/день для 2 років, +100 грн за кожен наступний рік.

| Вік | Харчування, грн/день |
|---|---|
| 2 | 300 |
| 3 | 400 |
| 4 | 500 |
| 5 | 600 |

- FR-26. Оплата щомісяця або за рік наперед. При оплаті за рік знижка 12%.
- FR-27. Система автоматично рахує вартість навчання, харчування, знижки й кінцеву суму до оплати.
- FR-28. У рахунку є лише дві статті: навчання і харчування.
- FR-29. Бажано зберігати історію оплат, знижок і змін вартості.

### 4.7. Фінансова аналітика (для Admin)

- FR-30. Розрахунок прибутку по кожній групі та загального прибутку.
- FR-31. Розрахунок мінімальної окупної кількості кімнат.
- FR-32. Система визначає умови отримання максимального прибутку та момент, коли збільшення кількості дітей уже не збільшує чистий прибуток.
- FR-33. Прибуток визначається як різниця між виручкою з урахуванням знижок і витратами на приміщення, зарплати, надбавки та харчування.

## 5. Модель даних (принцип)

MongoDB використовується за принципами нормалізованої SQL-бази даних.

Кожна основна сутність зберігається в окремій колекції. Зв'язки між документами реалізуються через ідентифікатори, а для зв'язків багато-до-багатьох використовуються проміжні колекції.

| Колекція | Зв'язки | Що зберігається |
|---|---|---|
| `users` | — | Логін, хеш пароля, роль |
| `parents` | `userId` | Дані батьків або опікунів |
| `children` | `groupId` | Ім'я, дата народження, родичі, вподобання |
| `child_parents` | `childId`, `parentId` | Зв'язки дітей із батьками |
| `groups` | `roomId`, `educatorId`, `assistantId` | Вік дітей, максимальна кількість |
| `rooms` | — | Назва, вартість приміщення |
| `staff` | `userId` | ПІБ, посада, зарплата |
| `subjects` | — | Назва гуртка |
| `staff_subjects` | `staffId`, `subjectId` | Зв'язки викладачів із гуртками |
| `lessons` | `groupId`, `subjectId`, `staffId` | День, час початку, тривалість |
| `discounts` | — | Тип пільги, відсоток знижки |
| `child_discounts` | `childId`, `discountId` | Призначені пільги |
| `meal_rates` | — | Вартість харчування за віком |
| `invoices` | `childId` | Рахунок за навчання та харчування |
| `payments` | `invoiceId` | Сума, дата та період оплати |

Пов'язані дані не зберігаються як вкладені копії інших сутностей. Для отримання інформації з кількох колекцій використовуються зв'язки між документами.

## 6. REST API (орієнтовно)

| Метод і ресурс | Опис | Хто |
|---|---|---|
| `POST /auth/login` | Вхід | Усі |
| `GET/POST /children`, `GET/PATCH/DELETE /children/{id}` | Діти | Admin, Manager; Parent лише дозволені дії зі своєю дитиною |
| `GET /children/{id}/invoice` | Сума до оплати | Admin, Manager, Parent своєї дитини |
| `GET/POST /groups`, `GET/PATCH /groups/{id}` | Групи | Admin, Manager |
| `GET/POST /staff`, `PATCH /staff/{id}` | Персонал | Admin |
| `GET /staff/{id}/schedule` | Розклад викладача | Teacher свій, Admin |
| `GET/POST /subjects` | Гуртки | Admin |
| `GET /groups/{id}/lessons`, `PATCH /lessons/{id}` | Розклад групи, редагування | Admin, Teacher; Parent читає розклад своєї дитини |
| `POST /schedules` | Згенерувати чернетку | Admin |
| `GET/POST /payments` | Історія та реєстрація оплат | Admin, Manager; Parent переглядає свої |
| `GET /reports/profit` | Прибуток (`?groupId=`) | Admin |
| `GET /reports/min-rooms` | Мінімальна окупна кількість кімнат | Admin |

## 7. Нефункціональні вимоги

- NFR-01. Сервер дотримується принципів REST.
- NFR-02. Паролі користувачів зберігаються у вигляді хешу.
- NFR-03. Права доступу перевіряються сервером.
- NFR-04. Розрахунки виконуються сервером, а не клієнтом.
- NFR-05. Кількість охочих необмежена, тому система не повинна бути жорстко прив'язана до певної кількості груп.
- NFR-06. MongoDB використовується за принципами нормалізованої SQL-бази даних.

## 8. Припущення

- A1. Місяць має 22 робочі дні для розрахунку харчування.
- A2. Пільгова знижка та знижка 12% за річну оплату застосовуються послідовно.
- A3. Базова зарплата вихователя та помічника становить 40 000 грн.
- A4. Один урок триває 30 хвилин.

Ці припущення використовуються до уточнення відповідних питань із викладачем.

## 9. Відкриті питання (потрібне рішення при погодженні)

1. Харчування розраховується за кожен день відвідування чи за фіксовану кількість робочих днів?
2. Пільгова знижка та 12% за річну оплату складаються чи застосовуються послідовно?
3. Яка базова зарплата вихователя та помічника?
4. Чи передбачена окрема знижка для кількох дітей однієї сім'ї, якщо вони є родичами Admin?
5. Скільки занять на день має одна група і яка тривалість одного заняття?
6. Що вважати окупністю: покриття щомісячних витрат чи повернення вкладень у купівлю приміщення?
7. Яка початкова кількість викладачів передбачена для кожного гуртка?

## 10. Критерії приймання

- [ ] API відповідає принципам REST.
- [ ] Для зберігання даних використовується MongoDB, нормалізована за принципами SQL.
- [ ] Дані розділені на окремі колекції зі зв'язками через ідентифікатори.
- [ ] Для зв'язків багато-до-багатьох використовуються проміжні колекції.
- [ ] Права ролей працюють, Parent не бачить чужі дані.
- [ ] Група не змішує дітей різного віку й не перевищує 20 дітей.
- [ ] Розклад без накладок викладачів, кожна група має доступ до всіх гуртків.
- [ ] Рахунок враховує пільгу, вік і річну знижку.
- [ ] `profit` і `min-rooms` повертають коректні значення.
- [ ] Система розраховує загальний прибуток та прибуток окремих груп.
- [ ] Бажано зберігати історію оплат і змін вартості.

# QA Test Cases — Коло №3

**Проєкт:** Kindergarten Management System  
**Відповідальний QA:** Гуменюк Денис  
**Коло тестування:** №3 — фінансові модулі та журнал аудиту  
**Дата створення:** 31.10.2026  
**Статус:** In Progress

## 1. Загальна інформація

**Мета:** перевірити сім модулів: Tuition, Invoices, Analytics, Meals, Payments, Salaries та Audit.

**Середовище:** Node.js / Express, MongoDB Atlas (`kindergarten_dev`), Prisma ORM, Bruno, Jest (за наявності конфігурації), `http://localhost:3000/api/v1`.

Тестування виконується на локальних гілках відповідних Pull Requests. Перед виконанням запитів звірити фактичні маршрути, параметри та JSON body з `*.routes.js` і `*.validation.js`. Цей документ не задає непідтверджені endpoint або payload.

Використовуються лише вигадані тестові дані. Не змінювати й не видаляти записи інших розробників.

**Статуси:** `Not Run` — не виконано; `Passed` — пройдено; `Failed` — невідповідність; `Blocked` — заблоковано; `Not Implemented` — функціональність відсутня.

Для кожного тесту записати фактичний результат, дату, гілку/PR та за потреби GitHub Issue.

### TC-R3-013 — Пільга не зменшує харчування

**Модуль:** Invoices  
**Тип:** Інтеграційний  
**Статус:** BLOCKED

**Передумови:** модуль доступний у перевіреній гілці; створено тестову знижку та підготовлено тестові дані.

**Кроки:**

Проте повноцінне інтеграційне тестування не виконано через відсутність API для призначення знижки дитині. Перевірку заблоковано через обмеження реалізації.

### Загальний висновок

У ході тестування модуля Invoices успішно перевірено створення місячних і річних рахунків, формування окремих складових вартості навчання та харчування, захист від дублювання, облік часткових оплат і контрольоване скасування рахунків.

Більшість перевірок завершилася успішно. Водночас виявлено обмеження: відсутній API для призначення знижок конкретним дітям, через що повноцінна перевірка впливу пільг на вартість харчування не виконана. Також окремий регресійний сценарій перевірки незмінності історичних тарифів і знижок підтверджено лише частково.

**Модуль:** Audit  
**Тип:** Позитивний, негативний

2. Перевірити фільтрацію за періодом.
3. Перевірити фільтрацію за типом сутності.
4. Перевірити фільтрацію за дією.
5. Перевірити одночасне використання декількох фільтрів.
6. Передати некоректні параметри фільтрації.

**Очікуваний результат:** Коректні параметри приймаються, результати відповідають заданим фільтрам, а некоректні значення відхиляються з відповідною помилкою валідації.

**Фактичний результат:** У Bruno перевірено отримання записів аудиту та фільтрацію за різними параметрами.

Успішно перевірено:

- PASS — отримання всіх записів аудиту (`200 OK`).
- PASS — фільтрація за періодом (`200 OK`). Після використання повного часового діапазону від `2026-11-01T00:00:00.000Z` до `2026-11-01T23:59:59.999Z` отримано 14 записів за вказаний день.
- PASS — фільтрація за типом сутності `Payment` (`200 OK`). Отримано 10 записів, усі з відповідним типом сутності.
- PASS — фільтрація за дією `CREATE` (`200 OK`). Отримано 4 записи, усі з відповідною дією.
- PASS — одночасне використання фільтрів за періодом, типом сутності `Payment` та дією `CANCEL` (`200 OK`). Отримано 3 записи, які відповідають усім заданим умовам.
- PASS — некоректна дія (`422 Unprocessable Entity`).
- PASS — некоректний діапазон дат (`422 Unprocessable Entity`).
- PASS — некоректний формат дати (`422 Unprocessable Entity`).
- PASS — тип сутності довжиною понад 100 символів (`422 Unprocessable Entity`).
- PASS — порожній тип сутності (`422 Unprocessable Entity`).
- PASS — тип сутності довжиною 100 символів (`200 OK`).

Під час перевірки фільтрації за періодом виявлено, що передавання дат без часу не охоплювало записи за весь день. Після зазначення повного часового діапазону фільтрація працювала коректно.

Усі перевірені запити повернули очікувані HTTP-статуси, а фактичний вміст результатів відповідав заданим фільтрам.

**Результати тестування:**
- Passed — 4 тест-кейси.
- Blocked — 0 тест-кейсів.
- TC-R3-050 — виконано 11 запитів перевірки валідації та додаткові перевірки фактичної роботи фільтрів.

Під час тестування підтверджено, що записи аудиту створюються після операцій із платежами, фільтри повертають відповідні записи, а функція `prepareSnapshot()` видаляє секретні поля з даних, що передаються для журналювання.

Водночас виявлено, що поле `actorId` у створених записах має значення `null`, тому ідентифікація користувача, який виконав операцію, потребує додаткової уваги. Також перевірка відсутності секретних даних проводилася на рівні окремої функції, а не повного інтеграційного сценарію з базою даних.

Отже, основні перевірки модуля Audit пройдено успішно, проте залишаються окремі моменти, які потребують доопрацювання або додаткової перевірки.

## 10. Примітки до виконання

- Точні endpoint, параметри та JSON body звіряти з фактичним кодом PR; не вигадувати маршрути й поля.
- Для тестів `Blocked` спочатку отримати погодження бізнес-правила або контракту.
- Для фінансових перевірок використовувати контрольні тестові дані з відомими сумами.
- Jest перевіряє ізольовану бізнес-логіку; Bruno перевіряє API та інтеграцію. Один тип тестування не замінює інший.
- Підтверджені дефекти переносити до окремого bug report. Не описувати припущення як дефекти.

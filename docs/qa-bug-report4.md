## Виявлені проблеми під час QA Round 4 — Analytics та виконані виправлення

Під час тестування модуля Analytics було виявлено три проблеми в розрахунках і формуванні звітів.

### 1. Неправильний розрахунок заборгованості в AN-005

**Проблема:**

Аналітичний звіт заборгованості враховував лише звичайні розподіли платежів через invoice.allocations. При цьому не враховувалися операції застосування кредитного балансу, відновлення кредиту та коригування рахунків.

У результаті повністю оплачений рахунок помилково відображався як такий, що має заборгованість.

**Що було змінено:**

У файлі analytics.service.js замість самостійного підрахунку суми платежів використано готову допоміжну функцію getInvoicePaidAmount() з billing/credit-balance.service.js.

Функцію було доповнено можливістю враховувати часову межу звіту endExclusive, щоб до розрахунку потрапляли лише операції відповідного періоду.

Також було збережено використання getEffectiveInvoiceAmount() для врахування останнього коригування суми рахунку.

**Результат:**

Після виправлення повністю оплачений рахунок виключається зі списку боржників. Чиста заборгованість становить 73 400 грн.

### 2. Відсутність розрахунку різниці показників у AN-006

**Проблема:**

Початкова реалізація getSummary() повертала показники основного періоду та повний звіт за порівняльний період у полі comparison. Однак окремий розрахунок різниці між показниками не виконувався.

Це не повністю відповідало очікуванню тесту, який передбачав повернення обох періодів та коректної різниці показників.

**Що було змінено:**

У функції getSummary() додано формування окремого об'єкта changes.

Для грошових показників реалізовано розрахунок різниці через BigInt, щоб уникнути втрати точності під час роботи з великими значеннями.

Для числових показників, таких як кількість рахунків, платежів і відвідувань, використано звичайне віднімання.

У відповіді API збережено поле comparison, а також додано changes.

**Результат:**

API повертає дані основного та порівняльного періодів і окремо розраховану різницю показників.

### 3. Неправильний розрахунок заборгованості в AN-007

**Проблема:**

У функції getGroupReport() заборгованість груп розраховувалася лише на основі invoice.allocations. Через це не враховувалися кредитні операції та коригування рахунків.

У результаті заборгованість у груповому звіті не збігалася із заборгованістю в аналітичному звіті AN-005.

**Що було змінено:**

У функції getGroupReport() замінено ручний підрахунок платежів на використання getInvoicePaidAmount() з billing/credit-balance.service.js.

Для розрахунку також передається period.endExclusive, щоб враховувати операції в межах вибраного звітного періоду.

**Результат:**

Заборгованість у груповому звіті після виправлення становить 73 400 грн і збігається з результатом AN-005.

### Загальний результат виправлень

У межах QA Round 4 було вдосконалено розрахунок заборгованості в аналітичних звітах, додано автоматичне обчислення різниці показників між періодами та забезпечено узгодженість фінансових даних між різними аналітичними методами.

Для повторного використання логіки розрахунку платежів і кредитних операцій застосовано спільну допоміжну функцію getInvoicePaidAmount(), що зменшує дублювання коду та ризик розбіжностей між звітами.

**### 4. Помилка визначення активного зарахування в MEAL-005**

**Проблема:**

Під час розрахунку вартості харчування сервер повертав `MEAL_CATEGORY_NOT_CONFIGURED`, хоча групі дитини була призначена категорія A4.

Причиною була неправильна обробка записів enrollment, у яких поле endDate було відсутнє.

**Що було змінено:**

У файлі `meals.service.js` змінено умову пошуку активних зарахувань. Замість перевірки `endDate: null` додано перевірку відсутності самого поля через `isSet: false`.

**Результат:**

Після виправлення сервіс почав правильно знаходити активне зарахування дитини, визначати категорію групи та відповідний тариф. Розрахунок харчування успішно виконується.

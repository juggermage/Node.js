## 2. Підтверджені дефекти

### BUG-01 — Parents: дані зникають після перезапуску сервера

- **Модуль:** Parents
- **Серйозність:** High
- **Статус:** Open
- **Передумови:** сервер запущений.
- **Кроки відтворення:**
  1. Виконати `POST /parents` із коректними даними; отримати `201 Created`.
  2. Перезапустити сервер.
  3. Виконати `GET /parents`.
- **Очікуваний результат:** створений запис зберігається і доступний після рестарту.
- **Фактичний результат:** `200 OK`, відповідь `{"success":true,"data":[]}`; запис відсутній.
- **Технічне спостереження:** у `parents.service.js` використовується масив у пам'яті `const parents = []`.
- **Рекомендація:** забезпечити постійне збереження в БД відповідно до архітектури проєкту.

### BUG-02 — Parents: фізичне видалення замість Soft Delete

- **Модуль:** Parents
- **Серйозність:** Medium
- **Статус:** Open
- **Підстава:** аналіз реалізації `parents.service.js`.
- **Фактична реалізація:** видалення через `splice` з масиву.
- **Очікуваний результат:** якщо Soft Delete передбачено вимогами проєкту, запис повинен позначатися як видалений, а не фізично зникати зі сховища.
- **Рекомендація:** узгодити модель Soft Delete і реалізувати її відповідно до вимог.
- **Примітка:** це зауваження до реалізації, а не окремий підтверджений негативний HTTP-тест.

### BUG-03 — ChildParent: несумісність форматів ID

- **Модулі:** Parents / ChildParent
- **Серйозність:** High
- **Статус:** Open
- **Кроки відтворення:**
  1. Створити батька через `POST /parents`; API повертає UUID, наприклад `d8e33c3e-b9ba-4b7d-9518-32ce1aabfb92`.
  2. Взяти існуючий `childId` із `GET /children` (24-символьний ObjectId).
  3. Виконати `POST /child-parent` із цими `childId`, `parentId` та `relation: "FATHER"`.
- **Очікуваний результат:** можна зв'язати реально створених батька та дитину.
- **Фактичний результат:** `422` через формат `parentId`: схема ChildParent вимагає 24-символьний ObjectId, а Parents повертає UUID.
- **Рекомендація:** узгодити формати ідентифікаторів та модель зберігання між модулями.
- **Вплив:** позитивні інтеграційні сценарії BLOCKED.

### BUG-04 — ChildParent: 500 INTERNAL_ERROR на маршрутах

- **Модуль:** ChildParent
- **Серйозність:** High
- **Статус:** Open
- **Передумови:** сервер запущений; ID у запитах мають коректний 24-символьний формат.

| Запит | Очікувано | Фактично |
|---|---|---|
| `GET /child-parent/child/6adcec157343d39eb310b159` | 200 | 500 `INTERNAL_ERROR` |
| `GET /child-parent/parent/507f1f77bcf86cd799439011` | 404, якщо запис відсутній | 500 `INTERNAL_ERROR` |
| `GET /child-parent/507f1f77bcf86cd799439011` | 404, якщо запис відсутній | 500 `INTERNAL_ERROR` |
| `PATCH /child-parent/507f1f77bcf86cd799439011/complete` | 404, якщо запис відсутній | 500 `INTERNAL_ERROR` |
| `POST /child-parent` із наведеним нижче JSON | 404 для неіснуючих сутностей | 500 `INTERNAL_ERROR` |

Тіло останнього POST:

```json
{
  "childId": "507f1f77bcf86cd799439011",
  "parentId": "507f191e810c19729de860ea",
  "relation": "FATHER"
}
```

- **Рекомендація:** перевірити логи сервера, доступність БД, виклики Prisma та обробку відсутніх записів; усунути причину 500.
- **Примітка:** точну причину 500 не встановлено.

### 6.3. Додаткові дефекти та ризики

#### BUG-06 — Employees: блокування створення активного працівника

- **Модуль:** Employees / Staff Assignments / Teacher Subjects.
- **Серйозність:** потребує уточнення за логами і схемою БД.
- **Статус:** Needs investigation.
- **Фактичний результат:** під час підготовки тестових даних виник конфлікт з унікальністю `userId` у Prisma/MongoDB; активного працівника для позитивних сценаріїв підготувати не вдалося.
- **Очікуваний результат:** можливість створити валідного активного працівника відповідно до вимог API.
- **Вплив:** позитивні сценарії призначень заблоковані.
- **Рекомендація:** перевірити Prisma-схему, індекси MongoDB і фактичний текст помилки; після виправлення повторити створення працівника та інтеграційні тести.
- **Примітка:** точний HTTP-статус цього збою в поточному підсумку не зафіксований; не приписувати йому непідтверджений код відповіді.

#### BUG-07 — Subjects: розбіжності між Joi-схемами та сервісом

- **Модуль:** Subjects.
- **Серйозність:** Medium (попередня оцінка).
- **Статус:** Code review finding; потребує окремого підтвердження API-тестами.
- **Фактична реалізація:** Joi-схеми існують, але не підключені до маршрутів; `subjects.service.js` генерує UUID, а `subjects.validation.js` очікує 24-символьні ObjectId; Joi дозволяє `status` для оновлення/фільтрації, але сервіс не реалізує таку поведінку; правила `description` різняться; обмеження довжини Joi не застосовуються сервісом.
- **Очікуваний результат:** єдині узгоджені правила валідації, форматів ID і підтримуваних полів.
- **Рекомендація:** узгодити API-контракт, сервіс та middleware; додати тести на граничні значення і `status`.

#### BUG-08 — Subjects / Teacher Subjects: потенційна несумісність сховищ та ID

- **Модулі:** Subjects, Teacher Subjects.
- **Серйозність:** High (якщо підтвердиться в інтеграційному сценарії).
- **Статус:** Code review finding; інтеграційний тест не завершено.
- **Фактична реалізація:** Subjects зберігає записи у масиві пам'яті й створює UUID, тоді як Teacher Subjects шукає предмети через `prisma.subject` і приймає MongoDB ObjectId.
- **Очікуваний результат:** предмет, створений через Subjects API, можна призначити викладачу через Teacher Subjects API.
- **Рекомендація:** використовувати спільне джерело даних і сумісні ідентифікатори; виконати наскрізний тест створення предмета й призначення його активному викладачу.

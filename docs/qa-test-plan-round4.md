# QA Test Plan — Kindergarten Management System

**Відповідальний QA:** Зорій Ярослава  
**Коло:** №4 — аудит, RBAC, авторизація, розклад, коригування рахунків, переплати, аналітика, оптимізація, відвідуваність і харчування  
**Інструмент:** Bruno  
**Backend:** Node.js / Express  
**База:** MongoDB Atlas, `kindergarten_dev`  
**ORM:** Prisma  
**Base URL:** `http://localhost:3000/api/v1`  
**Статус:** Test Plan Prepared — Execution Pending

## 1. Мета тестування

Перевірити нову та доопрацьовану функціональність поточного кола, коректність бізнес-логіки, валідацію, контроль доступу, збереження даних у MongoDB та взаємодію модулів.

Тестування виконується вручну через Bruno. Наявні запити з Bruno-колекції повторно використовуються для регресії. Старі CRUD-сценарії не дублюються без потреби.

## 2. Середовище та підготовка

1. Перемкнутися на гілку відповідного Pull Request.
2. Переконатися, що `.env` використовує тестову БД `kindergarten_dev`.
3. Запустити сервер: `npm run dev`.
4. Перевірити `GET /health`.
5. У Bruno встановити `baseUrl=http://localhost:3000/api/v1`.
6. Підготувати тестові токени Admin, Manager, Parent, Teacher, Educator та Assistant.
7. Створити окремі тестові записи: батьків, дітей, групи, працівників, кімнати, рахунки, платежі, тарифи й витрати.

Використовувати лише вигадані дані. Не змінювати чужі записи, не запускати reset або `prisma db push` під час API-тестування без погодження. Не зберігати паролі та JWT у спільних файлах або скриншотах.

## 3. Інтеграційні блокери, знайдені в наданому ZIP

У `src/app.js` не знайдено підключення таких роутерів, хоча файли маршрутів у проєкті є:
- `auth.routes.js`;
- `attendance.routes.js`;
- `optimization.routes.js`.

Тому перед тестуванням потрібно перевірити, чи додані вони у гілку, яку тестуємо. Якщо ні, API-запити можуть повертати `404 ROUTE_NOT_FOUND`. Не позначати такі перевірки Passed.

Очікувані префікси для перевірки після інтеграції:
- Auth: `/api/v1/auth` (шляхи register/login/me/logout визначені у завданні).
- Attendance: `/api/v1/attendance` (потрібно узгодити префікс із розробником).
- Optimization: `/api/v1/optimization` (потрібно узгодити префікс із розробником).

## 4. Обсяг тестування

### 4.1 Prisma та структура даних
- Attendance — зв'язки з Child та Employee, `absenceReason`, унікальність `childId + date`.
- Group — `mealCategory` зі значеннями A2, A3, A4, A5.
- MealRate — категорія та сумісність зі старими тарифами за `ageYears`.
- InvoiceAdjustment, CreditBalance, CreditBalanceTransaction — зв'язки та збереження фінансової історії.
- Перевірити одиниці сум у фінансових відповідях (`moneyUnit`, зокрема `kopecks`).

### 4.2 Audit
- Фіксація CREATE, UPDATE, DELETE, CANCEL та інших підтримуваних дій.
- `actorId`, `action`, `entityType`, `entityId`, `before`, `after`, `createdAt`.
- Фільтрація за actorId, action, entityType і періодом.
- Пагінація та отримання запису за ID.
- Відсутність паролів, токенів та інших секретів у snapshots.
- Заборона доступу звичайним ролям.
- Відсутність API для редагування/видалення журналу.

### 4.3 Auth та RBAC
- Реєстрація, нормалізація email, захист від дублювання.
- Login з правильними та неправильними даними.
- JWT, `/me`, logout та відкликання попереднього токена.
- Ролі Admin, Manager, Parent, Teacher, Educator, Assistant.
- HTTP 401 без авторизації та HTTP 403 за недостатніх прав.

### 4.4 Schedules
- Створення DRAFT-розкладу.
- Автоматична генерація для активної групи з дітьми, кімнатою та доступним викладачем.
- Наявність навчальних занять, харчування та денного сну.
- Конфлікти груп, кімнат, викладачів і часу.
- Редагування, публікація, скасування елемента з причиною.
- Негативні сценарії: порожня група, перевищена місткість, невідповідний вік, відсутня кімната/викладач.

### 4.5 Billing — коригування та переплати
- Створення окремого документа коригування з посиланням на початковий рахунок.
- Причина, попередня та скоригована сума.
- Незмінність початкового рахунку та правильний перерахунок боргу.
- Перегляд історії та скасування коригування.
- Створення переплати й зарахування надлишку до кредитного балансу батьків.
- Часткове/повне використання кредиту, залишок балансу.
- Відновлення кредиту після скасування.
- Захист від повторного зарахування через `idempotencyKey`.
- Один платіж на кілька рахунків.

### 4.6 Analytics
- `/summary`, `/income`, `/expenses`, `/debts`, `/profitability`, `/groups`, `/attendance`.
- Звіти за місяць, квартал, рік і довільний період.
- Порівняння періодів.
- Доходи від навчання та харчування; нарахування окремо від фактичних надходжень.
- Витрати за категоріями, зарплати та FOOD.
- Оплачені/неоплачені рахунки, борги, рейтинг груп.
- Фактичний і модельний прибуток.
- Врахування коригувань та кредитних операцій без подвійного підрахунку.

### 4.7 Optimization
- Базовий звіт за період.
- Кількість дітей, груп, працівників і приміщень.
- Нормативна вартість приміщення 50 000 грн за місяць.
- Порівняння сценаріїв, рейтинг та найвигідніша конфігурація.
- Попередження для неможливих сценаріїв та валідація дат.

### 4.8 Attendance та Meals
- Створення, перегляд, редагування і видалення відвідуваності.
- Причина відсутності.
- Дублікат однієї дитини за одну дату.
- Підрахунок PRESENT і LATE як фактичної присутності.
- Фільтри за дитиною, групою, датою та статусом.
- Тариф, чинний на дату відвідування.
- Розрахунок вартості за фактичними днями.
- Витрати FOOD у фінансовій аналітиці.

## 5. Наявні Bruno-тести та доповнення

У наданій колекції вже є запити для Audit, Analytics, Meals, Invoices, Payments, Schedules, Salaries, Expenses та інших старих модулів. Їх потрібно використовувати для регресії, а не копіювати без потреби.

Не знайдено окремих Bruno-папок/наборів для Auth, Attendance, Optimization, Invoice Adjustments, Credit Balance / Apply Credit, Schedule Generation / Publish та нових звітів Analytics.

У старих Meals-запитах є поле `attendedDays`. Актуальна схема `POST /meals/calculate` приймає `childId`, `periodStart`, `periodEnd` та необов'язковий `ageYears`; фактичні дні беруться з Attendance. Старі запити потрібно оновити під актуальний контракт.

## 6. Види тестування

- Позитивне — валідні дані та успішні операції.
- Негативне — некоректні дані, дублікати, відсутні записи, недостатні права.
- Граничне — нульові значення, межі дат і періодів.
- Інтеграційне — Attendance → Meals → Analytics; Payments → CreditBalance → Invoices; бізнес-операції → Audit.
- Регресійне — повторний запуск наявних Bruno-запитів для змінених модулів.

## 7. HTTP-статуси

| Код | Значення |
|---|---|
| 200 | Успішне отримання/оновлення |
| 201 | Створення |
| 204 | Видалення без тіла |
| 400 | Некоректний запит |
| 401 | Неавторизований |
| 403 | Недостатньо прав |
| 404 | Не знайдено |
| 409 | Конфлікт/дублікат |
| 422 | Помилка валідації |
| 500 | Внутрішня помилка |

Очікувані статуси звіряти з актуальним контрактом. Не змінювати очікуваний результат після тесту лише для отримання Passed.

## 8. Порядок виконання в Bruno

1. Відкрити колекцію `Node.js QA Testing`.
2. Налаштувати окреме QA-середовище з `baseUrl`.
3. Токени різних ролей зберігати в локальному середовищі Bruno, не в спільній колекції.
4. Виконувати сценарії за залежностями: Auth/RBAC → тестові дані → Attendance/Meals → Invoices/Payments/Credit → Analytics/Optimization → Audit.
5. ID створених записів переносити в Bruno Environment Variables або використовувати з відповідей попередніх запитів.
6. Після POST/PATCH перевіряти результат GET-запитом.
7. Для кожного тесту зберігати HTTP-статус, response body та скриншот.
8. Після скасування перевіряти баланс, рахунок і Audit.
9. Після виправлень повторювати Failed-тест і пов'язані регресійні сценарії.

## 9. Статуси

| Статус | Значення |
|---|---|
| Not Run | Не виконано |
| Passed | Відповідає очікуванню |
| Failed | Виявлена невідповідність |
| Blocked | Є перешкода для виконання |
| Not Implemented | Функціональність відсутня |



## 10. Unit Testing — модульне тестування

**Мета:** Перевірити правильність роботи окремих компонентів backend частини системи за допомогою автоматизованих модульних тестів.

**Що необхідно виконати:**

1. Підготувати набори Unit-тестів для основних модулів системи, зокрема авторизації, користувачів, дітей, батьків, груп, працівників, розкладу та інших функціональних частин.
2. Перевірити правильність виконання основної бізнес-логіки сервісів, включаючи створення, редагування, отримання та видалення даних.
3. Перевірити валідацію вхідних даних, обробку некоректних значень, відсутніх параметрів та інших помилкових ситуацій.
4. Перевірити роботу контролерів: правильність виклику сервісів, формування відповідей API та повернення відповідних HTTP-статусів.
5. Перевірити налаштування маршрутів, доступ до endpoint-ів, авторизацію та перевірку прав користувачів.
6. Перевірити граничні випадки та можливі помилки в розрахунках, фінансових операціях, відвідуваності й аналітиці.
7. Використати Jest для автоматизованого виконання тестів та моки для ізоляції окремих компонентів від зовнішніх залежностей.

**Очікуваний результат:** Наявність автоматизованих Unit-тестів для основних модулів системи, які підтверджують правильність роботи окремих компонентів та обробки помилкових ситуацій.

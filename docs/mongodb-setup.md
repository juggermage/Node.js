# MongoDB — налаштування бази даних для команди

## 1. Загальна інформація

У проєкті **Kindergarten Management System** використовується MongoDB Atlas для зберігання даних та Prisma ORM для взаємодії з базою даних.

**Параметри проєкту:**

- **СУБД:** MongoDB Atlas
- **Кластер:** `kindergarten-cluster`
- **Основна база:** `kindergarten_db`
- **Тестова база:** `kindergarten_dev`
- **ORM:** Prisma 6.19.3
- **Кількість колекцій:** 25
- **Файл схеми:** `prisma/schema.prisma`

Основна база даних уже створена та налаштована. Повторно створювати колекції або індекси кожному розробнику не потрібно.

Усі учасники, які підключаються до `kindergarten_db`, працюють зі спільними даними.

## 2. Підключення до MongoDB

### Крок 1. Отримання доступу

Для підключення необхідно отримати від відповідального за базу даних:

- Доступ до MongoDB Atlas.
- Рядок підключення `DATABASE_URL`.
- Дозвіл на підключення з власної IP-адреси, якщо цього вимагають налаштування Atlas.

**Заборонено публікувати логіни, паролі та повний рядок підключення у GitHub.**

### Крок 2. Налаштування `.env`

У кореневій папці проєкту створити або відкрити файл `.env`.

Додати змінну:

```env
DATABASE_URL="mongodb+srv://USERNAME:PASSWORD@CLUSTER_ADDRESS/kindergarten_db?retryWrites=true&w=majority"
```

Замість `USERNAME`, `PASSWORD` і `CLUSTER_ADDRESS` використати отримані параметри підключення.

Файл `.env` не повинен потрапляти до Git.

Для локальних експериментів рекомендовано використовувати окрему базу, а не спільну `kindergarten_db`.

## 6. Особливості індексів MongoDB

У колекціях `parents` та `employees` поле `userId` є необов'язковим.

У Prisma воно визначене так:

```prisma
userId String? @unique @db.ObjectId
```

Проте звичайний унікальний індекс MongoDB не дозволяє зберігати декілька документів без `userId`.

Тому в основній базі вручну створено два **часткові унікальні індекси (Partial Unique Indexes)**.

### Колекція `parents`

**Назва індексу:**

```text
parents_userId_partial_unique
```

**Index Fields:**

```json
{
  "userId": 1
}
```

**Partial Filter Expression:**

```json
{
  "userId": {
    "$type": "objectId"
  }
}
```

**Unique:** `true`

### Колекція `employees`

**Назва індексу:**

```text
employees_userId_partial_unique
```

**Index Fields:**

```json
{
  "userId": 1
}
```

**Partial Filter Expression:**

```json
{
  "userId": {
    "$type": "objectId"
  }
}
```

**Unique:** `true`

Ці індекси дозволяють створювати декілька батьків або працівників без облікового запису, але забороняють прив'язувати один `userId` до декількох записів у межах відповідної колекції.

Звичайні індекси `parents_userId_key` та `employees_userId_key` були видалені після створення часткових.

## 7. Важливе правило щодо `prisma db push`

**Не запускайте самостійно команду:**

```powershell
npx prisma db push
```

на основній базі `kindergarten_db`.

Причина: Prisma може повторно створити звичайні унікальні індекси для `parents.userId` та `employees.userId`, що порушить очікувану поведінку необов'язкових полів.

Крім того, `db push` може змінювати структуру колекцій та індексів відповідно до поточного стану `schema.prisma`.

### Дозволені команди

```powershell
npx prisma validate
npx prisma generate
npm run dev
```

### Зміни структури бази

Якщо необхідно додати модель, поле, зв'язок або індекс:

1. Внести зміни до `prisma/schema.prisma` у власній Git-гілці.
2. Виконати `npx prisma validate`.
3. Перевірити зміни на окремій тестовій базі.
4. Створити Pull Request.
5. Узгодити зміни з Team Lead та відповідальним за MongoDB.
6. Перед застосуванням змін до основної бази перевірити їхній вплив на дані та індекси.
7. Після узгодженого оновлення перевірити часткові індекси `parents` і `employees`.

**Не використовувати `--force-reset` або `--accept-data-loss` на основній базі без окремого погодження та резервної копії.**

## 8. Відновлення часткових індексів

Якщо після зміни схеми або виконання `db push` знову з'явилися звичайні індекси:

```text
parents_userId_key
employees_userId_key
```

не потрібно одразу видаляти їх.

Спочатку перевірити дані, наявні індекси та можливі конфлікти.

Порядок відновлення:

1. Відкрити MongoDB Atlas → Data Explorer.
2. Вибрати `kindergarten_db`.
3. Перевірити вкладку **Indexes** у `parents` та `employees`.
4. Переконатися, що часткові унікальні індекси існують, мають правильні параметри та статус `READY`.
5. Після погодження з відповідальним за базу видалити лише зайві звичайні індекси.

Не видаляти системний індекс `_id_` та інші індекси, які використовує проєкт.

## 10. Тестова база даних `kindergarten_dev`

### 10.1. Призначення тестової бази

Для розробки, перевірки та тестування функціональності проєкту використовується окрема база даних `kindergarten_dev`, розміщена в MongoDB Atlas на кластері `kindergarten-cluster`.

**Основні бази даних:**

| База даних | Призначення |
|---|---|
| `kindergarten_db` | Основна спільна база даних команди |
| `kindergarten_dev` | Тестова база для розробки та перевірки функціональності |

Тестова база має ту саму Prisma-схему, що й основна база, але містить окремі дані.

Використання `kindergarten_dev` дозволяє перевіряти нові функції, створювати тестові записи, виконувати CRUD-операції та виявляти помилки без впливу на основні дані команди.

**Тестова база не є копією основної бази та не синхронізує з нею дані автоматично.**

### 10.2. Підключення до тестової бази

Для роботи з тестовою базою потрібно відкрити файл `.env` у корені проєкту.

Приклад рядка підключення:

```env
DATABASE_URL="mongodb+srv://USERNAME:PASSWORD@CLUSTER_ADDRESS/kindergarten_dev?retryWrites=true&w=majority"
```

Для підключення до основної бази використовується назва:

```text
kindergarten_db
```

Для підключення до тестової бази:

```text
kindergarten_dev
```

**Важливо:** перед виконанням операцій створення, оновлення або видалення тестових записів необхідно переконатися, що підключена саме `kindergarten_dev`.

Для перевірки поточної бази виконати в PowerShell:

```powershell
node -r dotenv/config -e "const u = new URL(process.env.DATABASE_URL); console.log('Database:', u.pathname.slice(1))"
```

Очікуваний результат:

```text
Database: kindergarten_dev
```

Ця команда виводить лише назву бази даних, не показуючи логін і пароль.

Після зміни `DATABASE_URL` потрібно перезапустити сервер застосунку.

### 10.3. Правила роботи з тестовою базою

У `kindergarten_dev` дозволяється:

- Створювати вигадані тестові записи.
- Перевіряти CRUD-операції.
- Тестувати пошук, фільтрацію та валідацію.
- Перевіряти зв'язки між моделями Prisma.
- Тестувати обробку помилок.
- Запускати Seed для створення початкових тестових даних.

**Заборонено використовувати реальні персональні дані дітей, батьків і працівників для тестування.**

Необхідно враховувати, що `kindergarten_dev` може використовуватися кількома учасниками команди. Тому не слід видаляти або змінювати чужі тестові записи без погодження.

Для автоматизованих тестів рекомендовано використовувати унікальні назви записів та очищувати лише дані, створені відповідним тестом.

Зміни структури бази через `prisma db push` навіть у тестовому середовищі необхідно узгоджувати, оскільки вони можуть вплинути на інших розробників та часткові унікальні індекси.

## 11. Початкові тестові дані (Prisma Seed)

### 11.1. Призначення Seed

Для автоматичного заповнення тестової бази початковими даними використовується файл:

```text
prisma/seed.js
```

Seed дозволяє створити необхідні тестові записи без ручного введення через API або MongoDB Atlas.

Це спрощує перевірку функціональності модулів Children, Groups, Rooms та інших компонентів системи.

Seed використовується лише для розробки та тестування і не є обов'язковим для запуску API.

### 11.2. Дані, які створює Seed

Поточна реалізація створює такі вигадані тестові записи:

| Колекція | Кількість | Приклади |
|---|---:|---|
| `rooms` | 2 | Seed Classroom A, Seed Music Room |
| `groups` | 1 | Seed Group A |
| `children` | 3 | Olena Koval, Andrii Melnyk, Sofiia Bondarenko |

Тестова група пов'язана з кімнатою `Seed Classroom A` через поле `mainRoomId`.

Усі тестові записи створюються відповідно до моделей, визначених у `prisma/schema.prisma`.

### 11.3. Запуск Seed

Перед запуском необхідно перевірити, що у файлі `.env` вибрана база:

```text
kindergarten_dev
```

Після цього в корені проєкту виконати:

```powershell
node prisma/seed.js
```

Очікуваний результат:

```text
Seeding database: kindergarten_dev
Rooms seeded
Groups seeded
Children seeded
Seed completed successfully
```

Це означає, що скрипт успішно опрацював початкові тестові дані.

### 11.4. Захист основної бази

У `prisma/seed.js` реалізована перевірка назви бази даних.

Якщо підключено `kindergarten_db` або будь-яку іншу базу замість `kindergarten_dev`, виконання Seed зупиняється з помилкою.

```javascript
if (databaseName !== "kindergarten_dev") {
  throw new Error(
    "Seed is allowed only for kindergarten_dev"
  );
}
```

Таким чином, поточна реалізація Seed призначена виключно для тестового середовища.

**Не потрібно видаляти або обходити цю перевірку для запуску Seed на основній базі.**

### 11.5. Повторний запуск та запобігання дублікатам

Для створення тестових записів використовується метод Prisma `upsert()`.

Він дозволяє:

- Створити запис, якщо його ще немає.
- Не створювати дублікат, якщо запис із відповідним унікальним значенням уже існує.
- Залишати наявні записи без змін завдяки `update: {}`.

Для перевірки унікальності використовуються:

- `name` — для кімнат.
- `name` — для груп.
- `childCode` — для дітей.

Тому повторний запуск:

```powershell
node prisma/seed.js
```

не повинен створювати дублікати тестових записів.

Ця властивість називається **ідемпотентністю**.

### 11.6. Результати перевірки Seed

Станом на 24.10.2026 Seed успішно протестовано на `kindergarten_dev`.

Після повторного запуску отримано:

```text
Seed rooms: 2
Seed groups: 1
Seed children: 3
```

Результати підтверджують, що повторне виконання не створило додаткових записів із визначеними у Seed унікальними значеннями.

Seed не виконує масового очищення колекцій і не видаляє записи інших розробників.

**Важливо:** якщо запис із таким самим унікальним значенням уже існує, Seed залишить його без змін. Тому для тестових даних використовуються спеціальні назви та коди з префіксом `Seed` або `SEED-`.

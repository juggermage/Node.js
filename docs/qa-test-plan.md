# QA Test Plan — Kindergarten Management System

**Проєкт:** Kindergarten Management System  
**Роль:** Quality Assurance (QA)  
**Відповідальний:** Гуменюк Денис  
**Коло тестування:** №2 — MongoDB Atlas, Prisma та перевірка бізнес-логіки  
**Статус:** In Progress  
**Дата створення:** 27.10.2026

## 1. Мета тестування

Метою QA-тестування є перевірка правильності роботи серверної частини Kindergarten Management System, відповідності функціональним вимогам та критеріям приймання AC-01–AC-18.

Основні завдання:

- Перевірити CRUD-операції REST API.
- Перевірити валідацію вхідних даних.
- Перевірити бізнес-правила та обмеження системи.
- Перевірити роботу MongoDB Atlas через Prisma ORM.
- Перевірити збереження даних та зв'язків між моделями.
- Перевірити обробку помилок і HTTP-статуси.
- Провести позитивне, негативне та граничне тестування.
- Перевіряти Pull Requests розробників.
- Виявляти, документувати та повторно перевіряти дефекти.
- Підготувати автоматизовані тести та підсумковий QA-звіт.

## 2. Середовище тестування

| Компонент | Значення |
|---|---|
| Операційна система | Windows 11 |
| Backend | Node.js, Express |
| База даних | MongoDB Atlas |
| Тестова база | `kindergarten_dev` |
| ORM | Prisma |
| API-клієнт | Bruno |
| Редактор | Visual Studio Code |
| Контроль версій | Git, GitHub |

## 3. Обсяг тестування

### 3.1. Children

- Створення, отримання, оновлення та видалення або архівування дітей відповідно до реалізації.
- Валідація обов'язкових полів.
- Перевірка дат народження та вікових обмежень.
- Перевірка унікальності `childCode`.
- Пошук і фільтрація дітей.
- Перевірка зв'язків із батьками та групами.

### 3.2. Rooms

- CRUD-операції кімнат.
- Перевірка унікальності назви.
- Валідація місткості.
- Пошук та фільтрація за статусом.
- Soft Delete через статус `ARCHIVED`.
- Перевірка заборони архівування кімнати, закріпленої за активною групою.

### 3.3. Groups

- Створення та оновлення груп.
- Перевірка вікових категорій.
- Обмеження місткості до 20 дітей.
- Заборона повторного активного зарахування.
- Переведення дітей між групами.
- Збереження історії зарахувань.
- Перевірка зв'язків із кімнатами.

### 3.4. Parents та Discounts

- CRUD-операції батьків.
- Перевірка контактних даних.
- Перевірка зв'язків дитини з двома батьками.
- Заборона видалення батька, пов'язаного з дитиною.
- Перевірка пільг та їхнього застосування.

### 3.5. Subjects та Employees

- CRUD-операції навчальних предметів.
- Валідація назв.
- Перевірка працівників.
- Призначення викладачів і працівників.
- Перевірка розрахунку зарплати.

### 3.6. Schedules та Expenses

- Створення та перегляд розкладу.
- Валідація часу початку й завершення.
- Виявлення конфліктів занять.
- Перевірка обліку витрат.
- Перевірка фінансових звітів.

### 3.7. Finance

- Розрахунок вартості харчування.
- Розрахунок оплати навчання.
- Застосування пільг.
- Створення рахунків.
- Перевірка повторних платежів.
- Збереження історичних рахунків після зміни тарифів.
- Перевірка фінансового прогнозу та звіту про прибуток.

## 5. Види тестування

**Позитивне тестування:** перевірка коректних запитів та очікуваних результатів.

**Негативне тестування:** перевірка некоректних даних, неіснуючих ID, дублікатів і порушень бізнес-правил.

**Граничне тестування:** перевірка мінімальних і максимальних допустимих значень, зокрема віку та місткості груп.

**Інтеграційне тестування:** перевірка взаємодії REST API, Prisma та MongoDB.

**Регресійне тестування:** повторна перевірка функціональності після змін у Pull Requests.

**Автоматизоване тестування:** unit- та інтеграційні тести для критичної бізнес-логіки.

## 6. Перевірка HTTP-статусів

Під час тестування перевіряються:

| Код | Призначення |
|---|---|
| 200 | Успішне отримання або оновлення |
| 201 | Успішне створення |
| 204 | Успішне видалення або архівування без тіла |
| 400 | Некоректний запит |
| 403 | Доступ заборонено |
| 404 | Ресурс не знайдено |
| 409 | Конфлікт даних або бізнес-правил |
| 422 | Помилка валідації |
| 500 | Внутрішня помилка сервера |

Точний очікуваний статус для кожного тест-кейсу визначається за актуальною API-специфікацією.

## 7. Правила роботи з MongoDB

Тестування виконується на базі `kindergarten_dev`.

Правила безпеки:

- Використовувати лише вигадані тестові дані.
- Не змінювати записи інших розробників без погодження.
- Не запускати `prisma db push` без узгодження.
- Не використовувати `--force-reset` або `--accept-data-loss`.
- Не публікувати `.env` та облікові дані.
- Для автоматизованих тестів створювати унікальні записи.
- Після тестування очищувати лише власні тестові дані, якщо це дозволяє логіка системи.

## 8. Порядок тестування Pull Requests

1. Отримати посилання на Pull Request.
2. Переглянути опис і змінені файли.
3. Визначити функції та критерії приймання, які зачіпає PR.
4. Підготувати позитивні, негативні та граничні тест-кейси.
5. Перевірити локальні зміни перед перемиканням гілки.
6. Запустити сервер та виконати API-тести через Bruno.
7. Перевірити збереження даних у MongoDB.
8. Зафіксувати фактичні результати.
9. Для підтверджених дефектів створити GitHub Issues.
10. Підготувати QA-звіт у коментарі до Pull Request.

## 9. Статуси тест-кейсів

| Статус | Значення |
|---|---|
| Not Run | Тест ще не виконувався |
| Passed | Фактичний результат відповідає очікуваному |
| Failed | Виявлено невідповідність |
| Blocked | Тест неможливо виконати через перешкоду |
| Not Implemented | Функціональність ще не реалізована |

Результати попередніх тестувань зберігаються окремо від результатів другого кола.

## 10. Критерії завершення тестування

Тестування Pull Request може вважатися завершеним, якщо:

- Перевірено всі доступні сценарії, що стосуються змін PR.
- Зафіксовано результати виконаних тестів.
- Для Failed-тестів описано кроки відтворення.
- Неперевірені сценарії та обмеження задокументовано.
- Підготовлено QA-звіт.
- Розробники отримали інформацію про знайдені дефекти.

Наявність неперевірених критичних сценаріїв або суттєвих дефектів зазначається у висновку QA.
